## Context

The work page grew by accretion: each feature that shipped (downloads, BibTeX, related reading,
timeline, revision history, provenance) added its own block between the heading and the text. No
single addition was large, but together they put 918px between the page top and Leibniz's first
word on a 768px viewport — measured in the browser preview, with the text panel starting at
`y=918`.

The page also serves three audiences at once, interleaved:

```
  readers    →  title · significance · the text · what to read next
  citers     →  BibTeX · the scan link
  builders   →  .tex · .sty · PDFs · model/effort provenance · changelog
```

Right now all three are stacked in the top 918px in no particular order. Most of the decisions
below fall out of separating them: reader material stays above the text, builder material moves to
where it is actually used, and anything that restates something else is deleted.

Constraints:

- `site/public/tex/` is git-ignored and generated by `write_tex_copy()` in
  `pipeline/build_site_data.py`, so the served `.tex` can differ from the corpus `.tex` at no cost
  to the corpus.
- `relatedNavHtml(bottom)` is deliberately one shared render path for both nav instances — the
  comment at `[id].astro:75` says so explicitly — so the two must not diverge structurally.
- `pop.js` is loaded globally from `Base.astro` and binds to any `.pop` wrapper on any page. New
  popovers need markup only, no new script.
- KaTeX and the deferred-typesetting machinery must keep working; nothing here touches the text
  transform or the `#en` / `#p-236` anchor scheme.

## Goals / Non-Goals

**Goals:**

- The first line of a work's text is visible in a 768px viewport without scrolling.
- Every element above the text earns its place: no fact is stated twice on the page.
- No corpus data changes — this is presentation only.
- Downloadable `.tex` compiles without a second file.
- Every URL, anchor, download path and search behaviour survives unchanged.

**Non-Goals:**

- Not folding the apparatus into a collapsed "About this edition" disclosure. That was explored and
  set aside: the scan link is what makes the project checkable, and hiding it behind a click is the
  wrong trade.
- Not moving `Next:` off the top of the page. Readers walking the development forward want it before
  the text, not only after.
- Not touching the revision history, the "report an error" links, the external-translations section,
  or the `ai-draft` notice.
- Not restyling the significance callout, the tabs, or the text itself.
- Not removing `scan_id`, `publication_full` or `edition` from the corpus YAML. They remain for
  validation, audit, and the copyright gate.

## Decisions

### 1. Delete `publication_full` from display; derive an edition note from `edition` instead

The obvious move is to delete both redundant fields outright. Checking all 18 works first showed
that would lose one real fact on three of them.

```
  edition.year == work.year   (15 works)  →  publication_full restates the header. Delete.
  edition.year != work.year   ( 3 works)  →  the scan is a later reprint. The header cannot say this.
      leibniz-1689-isochrona      1689 → Gerhardt, c.1858
      fagnano-1718-lemniscata     1718 → Opere Matematiche, 1911
      fagnano-1718-lemniscata-ii  1718 → Opere Matematiche, 1911
```

So the rule is conditional, not a flat delete: render a short parenthetical only when
`edition.year !== work.year`. Four words replace two lines, and the fact that survives is the one
the header structurally cannot carry.

*Alternative considered:* keep `publication_full` but truncate it. Rejected — it is free prose in
the YAML with no guaranteed shape, so truncation would be arbitrary. Deriving from `edition.year`
is a structured test with a predictable output.

**Settled during implementation.** This section first proposed rendering `(Gerhardt reprint, 1858)`.
That is not derivable: `edition` carries only `{year, is_transcribed_edition, rights_cleared,
rights_note}`, and the editor's name appears solely inside `rights_note` — the same unshaped free
prose the paragraph above rejects parsing. Three options were put to the user: year only, an
optional new `edition.short` field on the three affected works, or dropping the note entirely.
**Year only** was chosen, so the line reads `(from the 1858 edition)`. It keeps the change's promise
of touching no corpus data, and still carries the fact that matters — this is not the first printing
— while the editor's identity stays one click away on the scan itself.

*Alternative considered:* surface `scan_id` as the link's `title` attribute at zero layout cost.
Rejected along with tooltips generally (decision 5).

### 2. Downloads move into the tab panels rather than collapsing in place

Three options were weighed for the 181px Downloads box:

| Option | Effect | Verdict |
|---|---|---|
| Collapse into `<details>` | −160px, one click to reach anything | Hides `.tex` behind a disclosure with no label telling you what is inside |
| Move below the text | −181px above the fold | A reader who came only for the file scrolls a whole memoir |
| Move into each tab panel | −181px, and downloads sit next to the text they belong to | **Chosen** |

The panel is where the choice is already made: you are looking at the Latin, so the Latin `.tex` is
what you want. It also merges with the `attribution()` line already rendered at the top of each
panel, so one row replaces two elements:

```
  ┌ Original (Latin) ┬ Translation (English) ┐
  └──────────────────┴───────────────────────┘
   ↓ .tex   ⧉ BibTeX        claude-opus-4-8 · reviewed DvdL
   ────────────────────────────────────────────────────────
   page 234
   III. De linea isochrona…
```

This also resolves a duplication the Downloads box forced: `Original (Latin)` currently appears in
the tab button, the Downloads row label, and the panel's `sr-only` heading. Inside a panel the tab
already names the text, so the row label is dropped. The `sr-only` heading stays — it carries the
`#original` / `#en` anchor that tabs, deep links and Pagefind sub-results depend on.

### 3. Inline the preamble into the served `.tex` rather than relocating the `.sty` link

Removing the Downloads box strands `readmasters.sty`: that row is its only mention anywhere on the
site, and every corpus `.tex` opens with `\usepackage{readmasters}`, so a download without it does
not compile.

```
  A. second chip in the panel row      →  free, but repeats a site-wide file on 18 pages × 2 panels
                                          and still has to explain itself
  B. document it on /contribute        →  someone who downloaded from a work page never goes there
  C. inline it in write_tex_copy()     →  the question disappears                        ← chosen
```

`readmasters.sty` is 53 lines, of which ~33 are comments. What remains is five `\RequirePackage`
lines (`amsmath`, `amssymb`, `graphicx`, `adjustbox`, `ulem` — all present in any TeX distribution)
and five `\newcommand` definitions. Substituting that body for the `\usepackage` line when writing
`site/public/tex/<id>/<name>.tex` makes the download self-contained, and deletes both the `.sty`
chip and its explanatory note without relocating anything.

Two properties worth naming:

- The corpus copy is untouched. `corpus-format`'s requirement that every `.tex` use
  `corpus/preamble/readmasters.sty` still holds; only the generated copy is flattened.
- Old downloads stay reproducible — they carry the macro definitions they were compiled against
  rather than silently tracking a moving `.sty`.

*Trade-off accepted:* the inlined block is 35 lines, since the per-macro comments are kept — they
explain markup (`\origpage`, `\uncertain`, `\ednote`) that a reader of the `.tex` will actually
meet in the text. **The feared cost turned out not to exist:** each transcription's provenance
comment sits *above* `\documentclass`, so it is still the first thing in the file; the macros land
below it, where the single `\usepackage` line used to be.

### 4. The relnav becomes a permanent three-slot rail

The standalone `See this work in the timeline →` line and the relnav are the same idea — where does
this work sit relative to the others — rendered as two stacked elements. Folding the timeline into
the nav's centre costs one line and fixes a layout problem at the same time: 6 of 18 works have no
`recommended_prev`, so their nav currently renders with a blank left half.

```
  before (no prev)                after (no prev)
  ┌──────────────────────┐        ┌──────────────────────────────┐
  │          Next: Bern… │        │      timeline  Next: Bern…   │
  └──────────────────────┘        └──────────────────────────────┘
  See this work in the timeline →
```

**The nav now renders unconditionally** (confirmed with the user). Today it renders only when there
is a recommendation, which would silently drop the timeline link from the 4 works that have neither
(`abel-1826`, `betti-1871`, `noether-1869`, `picard-1885`) and from the bottom of 3 more that have a
prev but no next. Since the middle slot always has content, the nav always has something to show.

The middle slot appears in **both** instances. Adding it to only one would break the invariant that
`relatedNavHtml(bottom)` is a single shared render path, which exists precisely so the two cannot
drift. The consequence — 7 works showing a bottom nav containing only `timeline` — is accepted: a
centred link to the map, shown to someone who just finished a text, is a reasonable thing to be.

*Alternative considered:* keep the standalone line as a fallback for works with no recommendations.
Rejected — two ways of reaching the same page, and the 22px line survives on exactly the pages with
the least on them.

### 5. The status badge uses `.pop`, not a `title` tooltip

`skimmed` and `ai-draft` are the only two status values. `ai-draft` gets a notice box explaining
itself; `skimmed` is jargon defined nowhere on the page.

A `title` attribute was considered first and **rejected**:

- no hover on touch devices — the text is simply unreachable on a phone
- not keyboard-reachable (focus does not trigger `title`)
- unselectable, uncopyable, unstyleable
- inconsistent screen-reader support

A tooltip is only acceptable for garnish, and an unexplained review level is not garnish. The site
already has the right mechanism: `.pop`, defined once in `pop.js` and loaded globally from
`Base.astro`, used by `\ednote` editorial notes, significance citations and asides, timeline node
cards, and the About epigraph. It answers every objection above — the marker is a real `<button>`,
a click pins it open so it works on touch, Escape closes it, and the script keeps the card inside
the viewport. `pop.js` binds to the whole `.pop` wrapper, so the badge itself becomes the trigger
with no new script.

Follow the `.signote` variant (`global.css:273-278` — baseline-aligned, bordered, accent hover)
rather than the superscript `.ednote` style: the trigger is a badge, not a footnote mark.

### 6. Absent PDFs render nothing

`original_pdf` is null for all 18 works; PDFs exist only after a deploy-time Tectonic run. The
italic `PDF on deploy` placeholder therefore renders on every download row of every work, and would
reach readers unchanged if a deploy build ever failed. `pdf_url()`'s docstring already describes the
intended behaviour — *"the work page simply omits the download link"* — so this aligns the template
with the pipeline's own stated contract rather than inventing a new rule.

### 7. "Download all as .bib" is removed

With per-artifact Copy buttons beside the source link and inside each panel, the whole-file download
was the third citation affordance on one page. Removing it also removes its click handler and the
`Blob`/`URL.createObjectURL` code path. The hidden `#bib-store` stays — the Copy buttons read from
it.

## Risks / Trade-offs

- ~~**Inlined macros precede the provenance comment in a served `.tex`**~~ → Did not materialise:
  the provenance comment precedes `\documentclass`, so it still opens the file. Verified by
  compiling a served `.tex` in an empty directory (3-page PDF, no `.sty` present).

- **`readmasters.sty` becomes unreferenced by any page** → It stays emitted to
  `site/public/tex/readmasters.sty` and served, so any existing external link or bookmark keeps
  working. Only the on-page chip goes.

- **Downloads are one click further away for a reader who wants the translation while viewing the
  original** → They must switch tabs first. Judged acceptable: switching tabs is how you read the
  translation anyway, and the previous consolidated list cost every reader 181px to serve that case.

- **Seven works get a bottom nav containing only `timeline`** → Accepted deliberately (decision 4)
  to preserve the shared-render-path invariant.

- **Pagefind indexing could shift** if the chip row lands inside `data-pagefind-body` → The chip row
  must sit inside the panel but carry `data-pagefind-ignore`, matching how `.pop` apparatus is
  already excluded from the index. Verify no chip text appears in search excerpts after the change.

- **Six requirements in `site-catalog` change at once**, three of them replacing existing scenarios
  → Deltas are written per requirement with the replaced scenarios named explicitly in the proposal,
  so the sync step has no ambiguity about what supersedes what.

## Migration Plan

No data migration. Corpus YAML and `.tex` are untouched, so the change is a rebuild:

1. `npm run data` regenerates `works.json` and rewrites `site/public/tex/` with inlined preambles.
2. `npm run build` produces the site; Pagefind re-indexes.

Rollback is a revert of the three source files followed by a rebuild — nothing persists between
deploys that would need undoing, since `site/public/tex/` and `site/public/pdf/` are both generated.

## Open Questions

None blocking. Two settled during exploration and recorded above for the record:

- Whether to fold everything into an "About this edition" disclosure — decided no (Non-Goals).
- Whether `Next:` is premature at the top of the page — decided no; readers walking the development
